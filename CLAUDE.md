## О проекте

Android-приложение из трёх разделов (Заметки / Задачи / Настройки) на Bottom Navigation.
Тестовое задание для стажёра — оценивается не объём, а качество: архитектура, читаемость,
обработка ошибок, обоснованность решений.

## Стек (обязателен, не менять без явного запроса)

- Kotlin, Jetpack Compose, Navigation Compose
- Retrofit + OkHttp + kotlinx.serialization
- Kotlin Coroutines + Flow
- Room — заметки и задачи; Preferences DataStore — настройки
- Hilt — DI
- Coil — изображения
- Material 3, простой дизайн, без кастомной графики

## Архитектура — модули и направление зависимостей

```
core:common        — ни от кого не зависит (чистый Kotlin, без Android SDK)
core:ui            — зависит только от core:common
core:network        — зависит только от core:common
core:database        — зависит только от core:common
core:datastore        — зависит только от core:common
core:permissions      — зависит только от core:common
core:navigation        — зависит только от core:common
core:media          — core:common, core:permissions
core:voice           — core:common, core:network
core:gigachat          — core:common, core:network
feature:notes / tasks / settings — зависят от нужных core:*, НИКОГДА друг от друга
app                — зависит от всех
```

Внутри каждого `feature:*`: пакеты `data` / `domain` / `presentation`.
Направление зависимостей внутри модуля: `presentation → domain ← data`.
Интерфейсы репозиториев — в `domain`, реализация — в `data`.
ViewModel никогда не обращается к DAO/Retrofit напрямую — только через UseCase.

## Конвенции именования и структуры

- UseCase: `ГлаголСущностьUseCase`, один метод `suspend operator fun invoke(...)`.
- Repository: интерфейс в `domain` без суффикса, реализация в `data` с суффиксом `Impl`.
- ViewModel: один `data class *UiState` на экран, наружу — `StateFlow<UiState>`,
  никаких публично видимых `MutableStateFlow`.
- Если у экрана больше двух вариантов состояния — `sealed interface`/`sealed class`,
  а не несколько независимых `Boolean`-полей.

## Категорически нельзя (типичные ошибки агентов на этом ТЗ)

- Хардкодить строки, цвета, dp, route-строки или секреты (см. раздел ниже).
- Делать создание задачи текстом через отдельный экран или BottomSheet — по ТЗ это должно
  происходить прямо инлайн в списке, новой строкой с активным полем ввода.
- Фильтровать список по каждому нажатию клавиши в поиске — поиск запускается только по
  кнопке поиска или клавише Search на клавиатуре, не реактивно посимвольно.
- Схлопывать разные ошибки в одно сообщение "что-то пошло не так" — например, 403 у
  GigaChat `/balance` (не тот тариф) и отсутствие сети — это разные состояния для пользователя.
- Молча проглатывать отказ в разрешении — всегда видимое состояние в UI; при permanent
  denial — путь в системные настройки приложения.
- Переписывать с нуля OAuth2/SSL для GigaChat — переносить существующее рабочее решение
  из pet-проекта gigachatpet, адаптируя под текущий DI/network-слой.
- Заводить новую стороннюю библиотеку без короткого обоснования в комментарии/README —
  по ТЗ сторонние библиотеки допустимы, только если оправданы и не подменяют реализацию
  ключевой функциональности.

## Хардкод — что и куда

| Что | Куда |
|---|---|
| Любой текст интерфейса | `strings.xml` |
| Отступы/размеры | токены `Spacing` в `core:ui`, не голые `.dp` в фичах |
| Цвета | только `MaterialTheme.colorScheme.*`, ни одного `Color(0xFF...)` в feature-модулях |
| Маршруты навигации | типизированные `@Serializable` route-классы в `core:navigation` |
| Секреты (GigaChat client_id/secret, ключ SaluteSpeech) | `local.properties` → `BuildConfig`, `local.properties` в `.gitignore` |
| Статусы (тема, фильтр задач, состояние записи) | `enum class` / `sealed interface`, не строки и не Int-флаги |

## Обработка ошибок

Единый `ApiResult<T>` (`Success` / `HttpError(code)` / `NetworkError` / `UnknownError`) и
`safeApiCall` в `core:network`, который ловит `IOException`/`HttpException`/
`SerializationException`. Любая ошибка должна доходить до пользователя понятным текстом,
а не проглатываться и не падать общим крашем.

## Минимальный набор состояний экрана

- Заметки: список / пусто / загрузка / ошибка сохранения / запись-обработка-ошибка
  голосового ввода.
- Задачи: список / пусто / текстовый инлайн-ввод / запись голоса / обработка голосового
  запроса / ошибка.
- Настройки: баланс GigaChat — загрузка / успех / ошибка (включая отдельно 403).

## Сборка и проверка

После каждого шага — `./gradlew assembleDebug` и просмотр диффа перед следующим шагом.
Опционально: unit-тесты на use case и один ViewModel (MockK + Turbine), без Compose UI
тестов — не тратить на них время сверх необходимого.
